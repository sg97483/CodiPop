## 2. 요금표 확정 시점에 대한 판단

### 결론: 파일럿 실사용 건수가 나오기 전까지 금액을 확정하지 않는다

지금 요금표를 확정하는 데 필요한 숫자가 없습니다. **몰 하나가 월에 피팅을 몇 건 쓰는지 근거가 0입니다.**
500건 / 2,000건 / 5,000건 구간이 실제 트래픽과 맞는지 확인할 방법이 없습니다.

- 실제로 몰당 월 80건이면 → STARTER 99,000원이 건당 1,238원짜리 바가지로 보임
- 반대로 월 3,000건씩 쓰면 → STARTER 고객이 추가 단가로만 50만 원을 내고 이탈

순서는 이렇게 걸려 있습니다.

```
로깅 → 파일럿 → 실사용 건수 확보 → 요금표 확정
```

로드맵상 프로모션으로 고객사를 확보하는 시점이 2026.11이므로, **확정 데드라인은 9월이 아니라 11월**입니다.

### 그럼에도 즉시 처리한 것 — 화질 등급 명시

금액 확정과 별개로, 슬라이드 15에는 구멍이 하나 있었습니다.
건수만 축으로 삼아 **품질 요구를 흡수하지 못하는 구조**였습니다.

이 상태로 사장님께 보여준 뒤 "합성 품질 좀 올려주세요"라는 요구가 오면,
약속한 적 없는 프리미엄 엔진을 **건당 12.4원 역마진**으로 제공하게 됩니다.

→ 금액은 그대로 두고 **"제공 화질(AI 엔진)" 열만 추가**해 프리미엄·2K를 ENTERPRISE 협의 항목으로 격리했습니다.

## 3. AI 합성 원가 — 실측 결과

운영 서버 실제 호출 로그 기준 (2026-08-08, 인물 1장 + 의류 1장, 환율 1,400원/USD):

```
입력 2,638 토큰 × $0.25/1M  =  $0.0007
출력 1,316 토큰 × $30.0/1M  =  $0.0395
─────────────────────────────────────
합계                          $0.0401  ≈  56.2원
```

### ⚠️ 공식 가격표만으로 계산하면 48원이 나오는데, 이는 17% 과소평가입니다

문서상 1K 출력은 1,120토큰이지만 **실측은 1,316토큰**이었습니다.
인물 사진이 세로형이면 결과 이미지도 세로 비율이 되어, 정사각형 기준보다 토큰을 더 씁니다.

**원가 논의에서 48원을 쓰지 마십시오.**

### 요금제 마진 (스탠다드 엔진 56.2원 기준)

| 플랜 | 월 기본료 | 풀사용 원가 | 매출총이익 | 이익률 | 추가 단가 마진 |
|---|---|---|---|---|---|
| STARTER | 99,000원 | 28,100원 | 70,900원 | 71.6% | +143.8원 |
| PRO | 290,000원 | 112,400원 | 177,600원 | 61.2% | +93.8원 |
| BUSINESS | 590,000원 | 281,000원 | 309,000원 | 52.4% | +43.8원 |

### 프리미엄 엔진(112.4원) 적용 시

| 플랜 | 추가 단가 | 건당 마진 |
|---|---|---|
| STARTER | 200원 | +87.6원 |
| PRO | 150원 | +37.6원 |
| **BUSINESS** | **100원** | **−12.4원 ← 역마진** |

대형 고객일수록 품질 요구가 높은데 정작 마진이 가장 얇은 구조입니다.
**프리미엄은 ENTERPRISE 협의로만 판매해야 합니다.**

### 알려진 한계

실측 표본이 적습니다(2건, 56.2원 / 55원대). 출력 토큰은 결과 이미지 비율에 따라 달라지므로 확정치가 아닙니다.
현재 모든 피팅이 토큰·처리시간·원가를 자동 기록하므로 **30일 누적 후 분포로 갱신**해야 합니다.

문서에는 보수적인 56.2원을 유지했습니다 (원가를 높게 잡는 쪽이 가격 판단에 안전).

## 4. 수익 구조 — 쇼핑몰 1개당 얼마를 버는가

3항의 실측 원가(건당 56.2원)를 요금제에 대입한 결과입니다.
**아래는 전부 매출총이익(AI 원가만 뺀 값)이며 순이익이 아닙니다.**

### 몰 1개 · 월 매출총이익

사용률 = 기본 제공 건수 대비 실제 사용 비율.

| 플랜 | 월 구독료 | 사용률 30% | 사용률 50% | 사용률 100% |
|---|---|---|---|---|
| STARTER | 99,000원 | 90,570원 (91.5%) | 84,950원 (85.8%) | 70,900원 (71.6%) |
| PRO | 290,000원 | 256,280원 (88.4%) | 233,800원 (80.6%) | 177,600원 (61.2%) |
| BUSINESS | 590,000원 | 505,700원 (85.7%) | 449,500원 (76.2%) | 309,000원 (52.4%) |

**AI 원가가 구독료 대비 작아 고객이 덜 쓸수록 마진이 커지는 구조입니다.**
STARTER 는 500건을 다 써도 원가가 28,100원뿐입니다.

기본 제공량을 **초과해도 이익은 계속 늘어납니다** — 추가 단가(200/150/100원)가
원가 56.2원보다 훨씬 높기 때문입니다. 150% 사용 시 STARTER 106,850원 / BUSINESS 418,500원.

### 첫해 기준 (초기 구축비 30만 포함, 사용률 50%)

| 플랜 | 첫해 수입 |
|---|---|
| STARTER | 약 132만원 |
| PRO | 약 311만원 |
| BUSINESS | 약 569만원 |

### ⚠️ 위 숫자에서 아직 빼지 않은 비용

| 항목 | 규모 |
|---|---|
| PG/카드 수수료 | 매출의 약 2.5% |
| Storage 저장·전송 | 건당 약 0.3원 |
| Render 호스팅 | 월 $7 ÷ 고객사 수 |
| **초기 구축 인건비** | 스크립트 지원 + 상품 이미지 검수 |
| **CS·운영 인건비** | 고객사 수에 비례 |
| **영업 인건비(CAC)** | 고객사 1곳 획득 비용 |

**초기 구축비 30만원은 순이익이 아닙니다.** 개발자 1인일 인건비가 30~40만원이면
초기 고객은 사실상 본전이고, 절차가 반복될수록 남습니다.

가장 큰 변수는 **영업 인건비**입니다. STARTER 한 곳은 월 8.5만원을 버는데,
그 한 곳을 따는 데 며칠이 걸리면 수지가 맞지 않습니다.

### 손익분기 — 월 고정비를 덮는 데 필요한 고객사 수

사용률 50% 가정, 위 기타비용 제외.

| 월 고정비 | STARTER만 | PRO만 | BUSINESS만 | 혼합(6:3:1) |
|---|---|---|---|---|
| 300만원 | 36개 | 13개 | 7개 | **19개** |
| 500만원 | 59개 | 22개 | 12개 | **31개** |
| 1,000만원 | 118개 | 43개 | 23개 | **61개** |
| 2,000만원 | 236개 | 86개 | 45개 | **121개** |

혼합 기준 **몰당 평균 월 매출총이익 166,060원**.

### 2027.12 목표 1,000개사 도달 시

믹스 STARTER 600 / PRO 300 / BUSINESS 100, 사용률 50% 가정.

```
월 매출          2억 540만원
월 매출총이익     1억 6,606만원
연 매출          24억 6,480만원
연 매출총이익     19억 9,272만원
```

### 여기서 나오는 두 가지 결론

**① 이 계산의 최대 불확실성은 여전히 "사용률"입니다.**
몰당 월 몇 건이 실제로 쓰이는지 근거가 없습니다. 30%와 100% 사이에서
STARTER 이익률이 20%p 넘게 벌어집니다. 2항의 "파일럿 전까지 요금표 확정 금지"와 같은 이유입니다.

**② 상위 플랜을 파는 것이 압도적으로 유리합니다.**
BUSINESS 1곳 = STARTER 5.3곳입니다. 영업 공수는 비슷한데 수익은 5배 차이이므로,
**영업 타깃 설정이 요금표 설계보다 중요할 수 있습니다.**
기획서 슬라이드 17의 "매출순위 3,000개 기업 리스트업" 전략과도 맞물리는 지점입니다.

## 5. 슬라이드 15(가격정책) 수정 내역

   - ENTERPRISE: `프리미엄 / 2K·4K 협의`

2. **표 하단 각주 2줄** — 화질 등급 기준, 초과분 후청구 및 대시보드 확인 안내
3. **프로모션 종료 조건** — `300,000원` → `300,000원 (선착순 100개사 한정)`
4. **커스텀 연동 공수 기준** — `(상담 후 결정)` → `(5인일 기준 · 초과 공수 별도 협의)`
5. **빨간 내부 메모 삭제** — "서비스 비용 합당한지 확인작업 필요"

**금액은 하나도 바꾸지 않았습니다** (2항의 판단에 따름).

고객 대면 문구는 "라이트" 대신 **"스탠다드"** 를 썼습니다 — "왜 나는 라이트를 받나"라는 반문을 피하기 위해서입니다.

## 6. 백엔드에 구축한 것 (배포·검증 완료)

상세는 `codipop-backend/README.md` 참조.

| 항목 | 내용 |
|---|---|
| 피팅 이벤트 로깅 | `fittingEvents` — 성공·실패 모두, 토큰·처리시간·**건당 원가** 포함 |
| 전환 추적 | `conversionEvents` — 구매 클릭까지. `/try-on` 응답의 `fittingEventId`로 귀속 |
| 몰별 통계 | `GET /stats/:mallId` — 슬라이드 21의 5개 항목 |
| 출력 해상도 고정 | `imageConfig.imageSize = '1K'` 명시 |
| 고객사별 엔진 등급 | `TENANT_TIERS` 환경변수. 미등록 몰은 항상 스탠다드 |

### 이 과정에서 고친 버그

**`firebase-admin.js`가 존재하지 않는 프로젝트(`codipop-6d2c0d`)를 가리키고 있었습니다.**
실제는 `codipop-63c0d`입니다. 오타 한 글자인데, 이 상태로는 Firestore 쓰기가 전부 실패합니다.
기존 `/get-recommendation`도 지금까지 동작한 적이 없었을 가능성이 높습니다 (앱이 호출하지 않아 드러나지 않음).

### 설계 판단 하나

"피팅했지만 안 산 상품"을 **절대 건수가 아니라 미구매율로 정렬**합니다.
절대 건수로 정렬하면 인기 상품이 상위를 차지해, 잘 팔리는 상품이 "안 팔리는 상품"으로 보입니다.

| 상품 | 피팅 | 구매 | 절대 차이 | 미구매율 |
|---|---|---|---|---|
| top-01 | 5 | 2 | 3 | 60% |
| bottom-01 | 3 | 0 | 3 | **100%** |

절대 차이는 동점이지만 MD에게 의미 있는 신호는 bottom-01입니다.

### 시각화 판단

- **헤드라인 숫자 4개는 차트가 아니라 스탯 타일**입니다. 값 하나를 막대 하나로 그리는 것은 잘못된 형태입니다.
- 막대는 **단일 계열이라 범례가 없습니다.** 제목이 계열을 지칭하고, 값은 막대 옆에 직접 라벨로 붙여
  색만으로 의미가 전달되지 않게 했습니다 (`aria-label` 에도 값 포함).

  명도밴드·채도·색각이상 분리·대비 검사를 모두 통과했습니다.
- **상품 ID 는 외부 입력이므로 렌더링 시 이스케이프**합니다 (XSS 테스트 포함).

## 10. Phase 2 — 임베드 위젯 + 고객사 API 키 (구현·검증 완료)

기획서 슬라이드 14의 설문 두 개가 이 작업의 이유입니다.

| 설문 결과 | 몰이 실제로 하는 말 | 이번에 만든 답 |
|---|---|---|
| **74.5%** — 연동이 복잡할 것 같다 | "개발자도 없는데 우리가 어떻게 붙이냐" | **스크립트 한 줄**. 상품 상세 템플릿에 `<script>` 하나 + 버튼 자리 `<div>` 하나 |
| **82.1%** — 누끼·재촬영이 부담된다 | "상품마다 배경 딴 이미지를 또 만들라고?" | **지금 쓰는 상품 사진 주소 그대로**. 이미지 가공 요구 없음 |

**연동 예시 페이지: https://codipop-backend.onrender.com/widget/example.html**
고객사에는 이 링크 하나만 보내면 됩니다. 붙일 코드와 속성 설명이 모두 들어 있습니다.

```html
<!-- ① 페이지 어딘가에 한 번 -->
<script src="https://codipop-backend.onrender.com/widget.js"
        data-codipop-key="pk_..." defer></script>

<!-- ② 버튼을 넣고 싶은 자리에 -->
<div data-codipop-button
     data-codipop-product="상품코드"
     data-codipop-name="상품명"
     data-codipop-price="39000"
     data-codipop-image="상품 이미지 주소"
     data-codipop-buy="구매/장바구니 주소"></div>
```

속성을 적지 않아도 동작합니다 — OG 태그 → 페이지에서 가장 큰 이미지 순으로 위젯이
스스로 찾습니다. 다만 리포트 정확도가 떨어지므로 상품 코드와 이름은 권장합니다.

### 설계 결정 세 가지

**① 피팅 화면은 iframe 안에 둔다.**
카페24·고도몰 스킨이 어떤 CSS 를 쓰는지 우리가 알 수 없습니다. 몰 페이지에 직접 DOM 을
그리면 스킨마다 깨지고, **그 대응 비용이 곧 "연동이 복잡하다"는 인식**이 됩니다.
iframe 은 CSS 가 양방향으로 격리되므로 어느 몰에 붙여도 같은 화면이 나옵니다.

**② 상품 이미지는 URL 로 받아 서버가 내려받는다.**
위젯은 몰 페이지의 이미지 *주소*만 알 뿐 파일을 갖고 있지 않습니다. 브라우저에서 그
이미지를 읽으면 **몰 CDN 의 CORS 에 막힙니다** — 카페24·고도몰 이미지 서버는
`Access-Control-Allow-Origin` 을 주지 않습니다. 서버에는 CORS 가 없으므로 여기서 받습니다.
82.1% 항목이 풀린 것은 이 결정의 부수 효과입니다.

**③ 구매 이동은 부모 창이 한다.**
iframe 안에서 주소를 바꾸면 몰 페이지는 그대로인 채 프레임만 이동해 장바구니 흐름이
깨집니다. iframe → 부모로 메시지를 보내고 부모가 이동시킵니다.

### 고객사 키 체계

키를 **두 종류로 분리**한 것이 이 작업의 핵심입니다. 성격이 정반대라 섞으면 사고가 납니다.

| 키 | 어디에 두는가 | 비밀인가 | 할 수 있는 일 |
|---|---|---|---|
| `apiKey` (`pk_...`) | 몰 페이지 `<script>` 태그 | **아니오 — 누구나 본다** | 피팅 요청만 |
| `dashboardToken` (`sk_...`) | 사장님에게만 전달 | **예** | 그 몰의 리포트 조회 |

`apiKey` 는 페이지 소스에 그대로 노출되므로 **비밀로 취급하면 안 됩니다.** 보호 수단은
허용 도메인 목록이며, 이 키로는 통계를 볼 수 없습니다.

**그동안 클라이언트가 보낸 `mallId` 를 그대로 믿고 있었습니다.** 아무나 남의 몰 이름으로
이벤트를 쌓아 리포트를 오염시킬 수 있는 상태였습니다. 이제 키가 있으면 **키가 가리키는
몰**로 기록하고 body 의 `mallId` 는 버립니다.

| 버튼 자동 주입 · 상품 정보 수집 | ✅ 속성 지정/자동 추론 양쪽 통과 (가격 `"39,000원"` → `39000` 숫자 추출 포함) |
| iframe 오버레이 · 스크롤 잠금 · 닫기 | ✅ |
| 남의 도메인에서 키 사용 | ✅ 차단 (`ORIGIN_NOT_ALLOWED`) |
| 와일드카드 도메인 `https://*.cafe24.com` | ✅ 통과 |
| body 의 `mallId=lirin` + 데모 키 | ✅ 무시되고 `demo-mall` 로 기록 |
| 없는 API 키로 `/try-on`·`/events` | ✅ 401 |
| **저스트원 토큰으로 리린 리포트 조회** | ✅ 차단 |
| SSRF — 사설망·메타데이터·`file://` | ✅ 전부 차단, 공개 이미지만 통과 |
| 이미지가 아닌 URL | ✅ 차단 (`application/json`) |

> **SSRF 방어를 반드시 유지할 것.** 주소를 받아 서버가 요청을 보내는 기능이므로,
> 사설 대역(`10.x` `192.168.x` `127.x`)과 클라우드 메타데이터(`169.254.169.254`)를
> 열면 자격증명이 노출됩니다. 리다이렉트도 우회 경로라 막아 두었습니다.
> `REMOTE_IMAGE_ALLOW_PRIVATE` 는 **로컬 개발 전용**이며 운영에 절대 설정하면 안 됩니다.
